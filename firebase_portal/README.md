# بوابة المستفيدين على Firebase

توسعة مستقلة للمشروع الحالي: Firebase Authentication لتسجيل الدخول، ووظيفة HTTP
واحدة للتحقق من الصلاحيات، وقاعدة Firestore مسماة `erp-portal` لا تسمح بقراءة
مباشرة من العملاء. لا تنشرها إلى مشروع عشوائي ولا تستبدل قواعد قاعدة `(default)`.

## ما تم تنفيذه

- واجهة متصفح عربية متجاوبة للهاتف والكمبيوتر.
- نسخة Windows منفصلة `lib/beneficiary_main.dart` لا تستورد ملف المدير أو بيانات المصنع.
- إدارة المستخدمين: ربط بمستفيد، عرض حقول محددة، تعديل حقول محددة، تصدير CSV، سحب الوصول.
- ملكية السجلات من اسم المستفيد في الحملات والمنتجات والحسابات، والإيميلات من الروابط
  المطابقة. السجلات المشتركة أو غير المرتبطة لا تُشارك إلا بربط يدوي من المدير.
- لا تُرفع كلمات المرور أو مفاتيح Gemini أو بيانات البنك الحساسة. تبقى محلية عند المدير.
- تحديث مباشر عبر SSE. الصلاحيات تُفحص في الخادم، بما فيها كل طلب تعديل. تغيير الصلاحيات
  أو التعطيل يصل للجلسات المفتوحة. تجديد رمز الدخول يتم عبر Firebase Auth REST.
- المزامنة تستخدم رقم إصدار: عند تعديل محلي وسحابي متزامنين يتوقف الاستبدال التلقائي
  ويطلب تطبيق المدير اختيار النسخة. لا تدّعي الواجهة نجاح الرفع عند انقطاع الشبكة.
- المعادلات المالية تعتمد على نفس تعريفات التطبيق: المتبقي = رأس المال - المصروف،
  الصافي = العمولة + المكافآت - المصروف. تُحسب القيم في الخادم.

## إعداد مشروع Firebase الصحيح

1. حدّد `projectId` الفعلي، والمستخدم الإداري الأول في Firebase Authentication.
   فعّل Email/Password من إعدادات Authentication إن لم يكن مفعّلًا. لا تغيّر حالة
   حسابات مشاريع أخرى. يوجد خيار ربط UID لمستخدم موجود بدل إنشاء حساب جديد.
2. يتطلب نشر Cloud Functions خطة Firebase تدعم الوظائف السحابية. لا يغيّر أي سكربت
   في المشروع إعداد الفوترة تلقائيًا.
3. استخدم موقع Hosting منفصلًا في المشروع نفسه؛ مثل `PROJECT-erp-portal`، وقاعدة
   مسماة مستقلة. اختر موقع Firestore المتوافق مع موقع مشروعك ووظائفك.

```powershell
firebase hosting:sites:create SITE_ID --project PROJECT_ID
firebase firestore:databases:create erp-portal --location us-central1 --project PROJECT_ID
node firebase_portal/configure.mjs --project PROJECT_ID --api-key PUBLIC_WEB_API_KEY --portal-url https://SITE_ID.web.app
```

`configure.mjs` يكتب معلومات Web العامة فقط. لا تضع مفاتيح حساب خدمة في التطبيق
أو مجلد `public`. يضبط رابط API وملف البيئة للوظيفة وهدف Hosting المستقل.

4. ثبّت تبعيات الوظيفة واختبرها، ثم انشر هذه التوسعة فقط:

```powershell
npm ci --prefix firebase_portal/functions
npm test --prefix firebase_portal/functions
firebase deploy --project PROJECT_ID --only firestore:rules,functions:erp-portal,hosting:erp-portal
```

لا تستخدم نشرًا عامًا لجميع وظائف أو مواقع المشروع القائم.

5. بعد إنشاء مستخدم مدير في Firebase Auth، شغّل bootstrap مرة واحدة باستخدام
Google Application Default Credentials المخوّلة لهذا المشروع:

```powershell
node firebase_portal/functions/bootstrap-admin.cjs PROJECT_ID FIREBASE_AUTH_UID
```

السكربت يرفض الكتابة فوق عضو موجود ولا يرسل بيانات تسجيل الدخول إلى أي عميل.

6. ابنِ المثبّت، ثم افتح «المستخدمون والمزامنة» في تطبيق المدير، وسجّل الدخول
بحساب المدير. اختر رفع المحلية أو اعتماد السحابية عند وجود نسخة سابقة. بعد
الاتصال، تُرفع التغييرات المحفوظة تلقائيًا. إدارة المستخدمين والصلاحيات متاحة
من بوابة المتصفح بزر داخل نافذة المزامنة.

7. سلّم المستفيد رابط البوابة أو مثبّت المستفيد فقط. لا تسلّم له نسخة المدير أو
قاعدة بياناته المحلية؛ التطبيق القديم محلي بالكامل ويحتوي بيانات المصنع.

## الاختبارات المحلية

لا تتصل هذه الأوامر بأي بيانات إنتاجية:

```powershell
$env:JAVA_HOME='C:\Program Files\Android\Android Studio\jbr'
$env:PATH="$env:JAVA_HOME\bin;$env:PATH"
firebase emulators:start --project demo-erp-portal --only auth,firestore,functions
node firebase_portal/functions/test/emulator-integration.cjs
```

الاختبار يستخدم حسابات `example.test` فقط، ويتحقق من عزل مستخدمين، إخفاء الحقول،
التحديث المباشر، سحب الوصول، منع الكتابة على بيانات الغير، رفض تضارب الإصدارات،
ومنع القراءة المباشرة من Firestore. لا تُستخدم بيانات المدير الحقيقية في الاختبارات.

رمز Telegram في هذا الإصدار. عند إضافته يلزم ربط Telegram ID بحساب Firebase
بموافقة المستخدم والتحقق من صلاحياته في كل طلب؛ لا تمنح البوت وصول مدير عام.

## حماية السجلات المحلية عند أول تشغيل

يُضاف معرّف مزامنة داخلي ثابت للحملات والبروكسي والحسابات البنكية، مع إبقاء
السجلات المتكررة منفصلة. قبل أول حفظ ينشئ التطبيق نسخة `.before_portal_ids.bak`
بجانب ملف البيانات. لا يعيد استبدال قاعدة موجودة ببيانات المصنع عند تعذّر قراءتها.
المعرّفات الداخلية ليست حقولًا متاحة للمستفيد. كلمات المرور ومفاتيح الاسترداد
وبيانات اتصال البروكسي السرية وIBAN لا تُرفع إلى بوابة المستفيدين.

تطابق الحسابات المالية نسخة المدير: تكلفة الحملات المعلقة تدخل ضمن المصروف
والمتبقي من رأس المال، بينما أرباحها وصافيها ينتظران وصول النتائج.

## إدارة الحسابات داخل تطبيق المدير

بعد تسجيل دخول المدير وتفعيل المزامنة، افتح «المستخدمون والمزامنة» ثم
«إدارة المستخدمين والصلاحيات داخل التطبيق». تستطيع إضافة مستخدم ببريد وكلمة
مرور أو ربط حساب موجود عبر UID، واختيار المستفيد ومؤشرات العرض وحقول التعديل
والتصدير وسحب الوصول. تغيير كلمة المرور متاح لحسابات المستفيدين المضافة إلى
البوابة فقط، مع تأكيد الكلمة الجديدة (12–128 حرفًا) وإلغاء الجلسات السابقة.
تغيير كلمة مرور Firebase يؤثر أيضًا على دخول الحساب نفسه في التطبيقات الأخرى
التي تستخدم حساب Authentication نفسه. لا تُحفظ كلمات المرور في مستندات البوابة.

## تحرير البيانات من الويب

من حساب المدير، افتح القسم ثم «إضافة سجل» أو أزرار «تعديل» و«حذف» في كل صف.
تكتب العمليات عبر API للمدير فقط، مع التحقق من الإصدار لمنع فقد التعديلات المتزامنة.
تصل التغييرات للتطبيق المتصل وللمستفيدين وفق صلاحياتهم. عند وجود تعديل محلي غير
مرفوع يعرض التطبيق تعارضًا للمراجعة. تبقى المعرّفات الطبيعية ثابتة عند التعديل
لحماية ارتباطات السجلات وكلمات المرور المحلية. لا يمكن حذف مستفيد مرتبط بسجلات
أو حسابات دخول أو ربط يدوي حتى تُنقل الارتباطات. كلمات المرور المحلية ليست حقولًا
قابلة للتحرير من هذه النماذج؛ إدارة كلمات مرور مستخدمي البوابة مستقلة عنها.
